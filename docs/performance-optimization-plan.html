性能优化改造方案

核心瓶颈「每次编辑触发全量拉取 + 全量重绘」的根治方案 · 含可落地代码 · 未改动仓库

一句话诊断

瓶颈不在 simple-mind-map 渲染本身，而在架构层：store 每次写操作后 reloadTree() 全量拉取（且并行发 nodes + tree 两个请求），叠加编辑器写完后 reloadMindMap() 全量 setData 重绘。你精心设计的 data_change_detail 增量同步，其收益被这两层全量刷新完全抵消。

改造 1：去掉写操作后的全量 reloadTree P0

API 的 create/update/move 已经返回最新 NodeDto，delete 语义明确。store 内直接用返回值维护 nodes，把 reloadTree() 从写方法里移除，让增量同步真正生效。

前端
frontend/src/stores/nodes.ts 
// create：返回值已够，无需全量 reload
async function create(payload: NodeCreatePayload): Promise<NodeDto> {
  const node = await nodesApi.createNode(mindMapId.value, payload)
  nodes.value.push(node)
  // await reloadTree()  ← 删除
  pushHistory({ type: 'create', nodeId: node.id, nextData: node })
  return node
}
// update / move：按返回的 updated 就地替换
const updated = await nodesApi.updateNode(mindMapId.value, nodeId, payload)
const idx = nodes.value.findIndex((n) => n.id === nodeId)
if (idx >= 0) nodes.value[idx] = updated
// await reloadTree()  ← 删除
pushHistory({ type: 'update', nodeId, prevData, nextData: updated })
// remove：本地过滤即可（后端已级联删除）
const allToDelete = [nodeId, ...collectDescendants(nodeId)]
await nodesApi.deleteNode(mindMapId.value, nodeId)
nodes.value = nodes.value.filter((n) => !allToDelete.includes(n.id))
// await reloadTree()  ← 删除

undo/redo 的 applyUndo/applyRedo 里的 reloadTree() 保留——那是整体重建场景，且它们会配合 reloadMindMap() 一起刷新画布。

注意：batchUpdate 的返回值是 void，无法就地更新。它目前被拖拽排序 / 批量展开折叠使用，这两种场景随后也会触发 reloadMindMap()（见改造 3），因此 batchUpdate 里的 reloadTree() 可一并删除，由调用方的整体重建兜底。

改造 2：后端递归删除 / 环检测改为「单查询 + 内存 BFS」P1

把 CollectDescendantsAsync（逐层查询）与 IsDescendantAsync（逐级向上查）改成一次拉出整张导图的 Id/ParentId，内存里收集，深导图删除从 N 次往返降到 1 次。

后端
backend/.../NodeService.cs 
/// 一次拉全量节点，内存 BFS 收集子孙 Id（替代逐层递归查询）
private async Task<HashSet<Guid>> CollectDescendantsOnceAsync(Guid mindMapId, Guid rootId, CancellationToken ct)
{
    var pairs = await _db.Nodes.AsNoTracking()
        .Where(n => n.MindMapId == mindMapId)
        .Select(n => new { n.Id, n.ParentId })
        .ToListAsync(ct);

    var childrenByParent = pairs
        .Where(p => p.ParentId.HasValue)
        .ToLookup(p => p.ParentId!.Value, p => p.Id);

    var result = new HashSet<Guid> { rootId };
    var queue = new Queue<Guid>();
    queue.Enqueue(rootId);
    while (queue.Count > 0)
    {
        var cur = queue.Dequeue();
        foreach (var cid in childrenByParent[cur])
        {
            if (result.Add(cid)) queue.Enqueue(cid);
        }
    }
    return result;
}
/// 环检测：由内存父子映射向上找祖先，不再逐级查库
private bool IsDescendantInMemory(Dictionary<Guid, Guid?> parentOf, Guid candidateId, Guid ancestorId)
{
    var current = candidateId;
    var visited = new HashSet<Guid>();
    while (current != Guid.Empty && visited.Add(current) && parentOf.TryGetValue(current, out var parent))
    {
        if (parent.HasValue && parent.Value == ancestorId) return true;
        if (!parent.HasValue) return false;
        current = parent.Value;
    }
    return false;
}

调用处：DeleteAsync 用 CollectDescendantsOnceAsync 替换递归；MoveAsync 先拉一次父子映射，再用 IsDescendantInMemory 替换 IsDescendantAsync。

改造 3：reloadMindMap 只用于「整体重建」P0

普通编辑（加节点、删节点、改样式、改内容、粘贴）后不应再 setData 整树重绘。这些操作要么已经通过增量同步的 data_change_detail 实时反映到画布，要么可以局部更新。

前端
frontend/src/views/editor/MindMapEditorView.vue
1
工具栏「新增子节点/同级」：改为直接操作画布，走增量同步
当前 handleAddChild 走「store.create → reloadMindMap」全量重建。更优路径：直接调用 simple-mind-map 的 INSERT_NODE 命令插入节点，让既有的 data_change_detail 增量同步负责落库，画布无需整体 setData。这也是库本身设计意图。
2
样式/内容更新：改完即已反映，无需 reloadMindMap
handleUpdateStyle / handleContentSave 里，样式与内容已经写进渲染节点（工具栏/弹窗直接改节点 data），删掉末尾的 reloadMindMap() 即可。节点文字、颜色由库即时重绘。
3
删除节点：可局部移除
submitNodeDelete 删除后可直接调用库的 REMOVE_NODE 或触发一次轻量重绘；若保留 reloadMindMap，需接受整树重建的代价。删除频率低，影响小于新增/编辑。
4
保留整体重建的场景（不动）
handleUndo / handleRedo / handleVersionRollback / initEmptyMindMap 这些确实需要后端状态整体覆盖画布，继续走 reloadMindMap()。
风险提示：改造 3 的步骤 1 需要核对 simple-mind-map 的 INSERT_NODE 命令参数与当前数据流是否完全兼容（尤其是「新增后立即改文字」的 pendingCreates 链路）。建议先落地改造 1 + 2（收益大、风险低），改造 3 分步验证后再推进。

改造 4：前端加索引缓存，消除 O(N²) 隐患 P1

为 nodes 维护 Map<id, node> 与 Map<parentId, children[]>，把 findNode / getChildren / collectDescendants / getDepth 从线性扫描降为 O(1) 查找。缓存随 nodes 增删同步维护。

前端
frontend/src/stores/nodes.ts 
// 索引缓存，随 nodes 变更同步维护
const nodeIndex = computed(() => {
  const m = new Map<string, NodeDto>()
  for (const n of nodes.value) m.set(n.id, n)
  return m
})

function findNode(id: string): NodeDto | undefined {
  return nodeIndex.value.get(id)
}

function getChildren(parentId: string | null): NodeDto[] {
  return nodes.value
    .filter((n) => n.parentId === parentId)
    .sort((a, b) => a.sortOrder - b.sortOrder)
}

其中 collectDescendants 用 shift() 是 O(N²)（shift 移动数组），改 queue 数组 + 指针递增，或直接复用上面后端同款 BFS。这类优化在拖拽、normalizeRootChildDirections 每次 layout 后跑的路径上效果明显。

改造 5：列表页封面查询在 SQL 侧收窄 P2

封面只要「根节点 + 前 4 个二级节点」，却查了每个导图的全部节点。把查询限制为根节点和二级节点两种候选行，可显著减少列表页对大树导图的拖累。

后端
backend/.../MindMapService.cs 
// 第一步：只取这些导图的根节点 Id
var rootIds = await _db.Nodes
    .Where(n => mapIds.Contains(n.MindMapId) && n.ParentId == null)
    .Select(n => n.Id)
    .ToListAsync(ct);

// 第二步：只取根节点 + 二级节点（而非全部节点）
var nodes = await _db.Nodes
    .Where(n => n.ParentId == null || (n.ParentId != null && rootIds.Contains(n.ParentId.Value)))
    .Where(n => mapIds.Contains(n.MindMapId))
    .Select(n => new { n.MindMapId, n.Id, n.ParentId, n.Title, n.SortOrder })
    .ToListAsync(ct);

其余组装逻辑不变（nodesByMap、SecondLevelCount 等），只是查出来的行数从「整树」降为「根 + 二级」。

落地顺序建议

1
改造 1（去 reloadTree）
收益最大、风险最低，先做。做完后单次编辑的请求量从「3 次全量」降到「1 次增量」，且增量同步真正生效。
2
改造 2（后端内存 BFS）
深导图删除/移动从 N+1 降到 O(1) 查询，独立后端改动，不影响前端。
3
改造 4（前端索引缓存）
消除高频路径的线性扫描，配合 1 一起验证。
4
改造 5（列表页收窄）
独立小优化，随时可做。
5
改造 3（reloadMindMap 只用于整体重建）
收益大但需验证命令兼容性，最后分步推进。

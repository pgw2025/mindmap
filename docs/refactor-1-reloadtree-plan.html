CbatchUpdate 的特殊处理（真正的副作用点）

核心风险batchUpdate 返回 void，且不更新本地 nodes。它有 2 个调用点，都在 useMindMapSync.ts：

调用点行号改了什么字段删 reloadTree 后本地 nodes 会怎样
applyExpandCollapse（批量展开/折叠）896isCollapsed⚠️ nodes[].isCollapsed 过期
handleStructuralChangesBatch（拖拽移动第二遍）1055sortOrder（parentId 已由第一遍 move 更新）⚠️ nodes[].sortOrder 过期

为什么这是风险：reloadMindMap()（useMindMapSync.ts:535）读的是 nodesStore.nodes，再 setData 覆盖画布。若 nodes 里 isCollapsed / sortOrder 过期，那么下一次任何触发 reloadMindMap 的场景（undo/redo、版本回滚）会用过期值覆盖画布——折叠状态回弹、排序错乱。

结论：batchUpdate 不能简单删掉 reloadTree() 了事，必须补上「本地同步」。见下 D 步的三种解法。

DbatchUpdate 的本地同步解法（三选一）

解法 1（推荐，最小改动）：batchUpdate 内根据 items 就地合并

batchUpdate 的 items 携带了要改的字段（id + sortOrder/parentId/isCollapsed/...），在 API 返回后把这些字段回填到 nodes 对应节点即可。

async function batchUpdate(items: NodeBatchItem[]): Promise<void> {
  const prevData = items.map((item) => nodes.value.find((n) => n.id === item.id)).filter(Boolean) as NodeDto[]
  await nodesApi.batchUpdateNodes(mindMapId.value, { nodes: items })
  // ← 新增：就地回填，替代原来的 reloadTree
  for (const item of items) {
    const node = nodes.value.find((n) => n.id === item.id)
    if (!node) continue
    if (item.sortOrder !== undefined) node.sortOrder = item.sortOrder
    if (item.parentId !== undefined) node.parentId = item.parentId
    if (item.isCollapsed !== undefined) node.isCollapsed = item.isCollapsed
    if (item.direction !== undefined) node.direction = item.direction
    // 其余样式字段同理，按需补 x/y/color/fontSize/... 等
  }
  pushHistory({ type: 'batch', snapshot: prevData, nextData: items })
}

注意：sortOrder 的重编是整组兄弟节点（不是单点），用「逐 item 回填」天然覆盖，因为 handleStructuralChangesBatch 已经把受影响父节点下全部兄弟都塞进了 items。

解法 2（更简单）：batchUpdate 后不刷新，但确保调用方随后 reloadMindMap

若调用方本身就会触发 reloadMindMap()（它会重新从 nodesStore.nodes 读——但注意读的也是旧 nodes，此路不通）。此解法不成立，因为 reloadMindMap 读的就是 nodes 本身，不能自举。故只保留解法 1 或 3。

解法 3（更彻底，但要动后端）：让 batchUpdate 返回最新 nodes

改后端 BatchUpdateAsync 返回受影响节点的完整 NodeDto 列表，前端用它替换 nodes 对应项。改动面更大（前后端 + DTO），非必要不选。

改造 2 最优方案：后端递归查询 → 内存索引

目标 backend/.../Application/Services/NodeService.cs · 不只是「N+1 → 单查询」，而是消除重复递归 + 环检测零额外成本

问题本质

两处递归查询，都在同一个文件里，且都只需要「某个导图的父子关系」：

方法行号现在怎么查代价
CollectDescendantsAsync（删除）452-466逐层 WHERE ParentId=x 递归深度 = N 次 DB 往返
IsDescendantAsync（移动环检测）433-450逐级 SELECT ParentId WHERE Id=current祖先链长度 = N 次 DB 往返

而 MoveAsync 里其实已经要拉兄弟节点（229/254/272 行），环检测完全可以在同一次查询里顺带完成。

核心思路：一个共享的内存父子索引

引入一个私有方法，一次性拉出整张导图的 (Id, ParentId)，返回 ToLookup<Guid?, Guid>（childrenByParent）和 Dictionary<Guid, Guid?>（parentOf）。这两个结构一个服务删除的「向下收集」，一个服务环检测的「向上回溯」。

为什么用 ToLookup：项目里 NodeService.BuildTree（521 行）和 MindMapVersionService.BuildTree（229 行）已经用 ToLookup(n => n.ParentId) 建树，改造 2 复用同一惯用模式，风格一致、可读性最好。

方案 A（推荐）：共享索引 + 内存 BFS 收集 + 内存回溯环检测

推荐一次查询，两个方法共用，删除与移动的递归全部消除。

/// 一次性拉取某导图的父子关系，返回 (childrenByParent, parentOf)。
/// 删除（向下收集子孙）与移动（向上回溯环检测）共用，消除 N+1。
private async Task<(ILookup<Guid?, Guid> Children, Dictionary<Guid, Guid?> ParentOf)>
    LoadParentRelationsAsync(Guid mindMapId, CancellationToken ct)
{
    var pairs = await _db.Nodes.AsNoTracking()
        .Where(n => n.MindMapId == mindMapId)
        .Select(n => new { n.Id, n.ParentId })
        .ToListAsync(ct);

    var children = pairs.ToLookup(p => p.ParentId, p => p.Id);
    var parentOf = pairs.ToDictionary(p => p.Id, p => p.ParentId);
    return (children, parentOf);
}

/// 内存 BFS 收集子孙 Id（替代逐层递归查询）
private static HashSet<Guid> CollectDescendants(ILookup<Guid?, Guid> children, Guid rootId)
{
    var result = new HashSet<Guid> { rootId };
    var queue = new Queue<Guid>();
    queue.Enqueue(rootId);
    while (queue.Count > 0)
    {
        var cur = queue.Dequeue();
        foreach (var cid in children[cur])
        {
            if (result.Add(cid)) queue.Enqueue(cid);
        }
    }
    return result;
}

/// 内存回溯判断 candidate 是否是 ancestor 的子孙（替代逐级查库）
private static bool IsDescendant(Dictionary<Guid, Guid?> parentOf, Guid candidateId, Guid ancestorId)
{
    var current = candidateId;
    var visited = new HashSet<Guid>();
    while (current != Guid.Empty && visited.Add(current))
    {
        if (!parentOf.TryGetValue(current, out var parent) || !parent.HasValue)
            return false;
        if (parent.Value == ancestorId) return true;
        current = parent.Value;
    }
    return false;
}

调用处改造 2：MoveAsync 环检测（206-219 行）

public async Task<NodeDto> MoveAsync(Guid userId, Guid id, NodeMoveRequest req, CancellationToken ct = default)
{
    ArgumentNullException.ThrowIfNull(req);
    var node = await GetOwnedNodeAsync(userId, id, ct);
    var oldParentId = node.ParentId;

    if (req.ParentId.HasValue)
    {
        if (req.ParentId.Value == id)
            throw ApiException.Conflict("不能将节点作为自身的子节点");

        // 防止环：新父节点不能是当前节点的子孙（旧，逐级查库）
        if (await IsDescendantAsync(req.ParentId.Value, id, ct))
            throw ApiException.Conflict("不能将节点移动到自身子孙下");
        // 防止环：一次拉父子索引，内存回溯（新）
        var (_, parentOf) = await LoadParentRelationsAsync(node.MindMapId, ct);
        if (IsDescendant(parentOf, req.ParentId.Value, id))
            throw ApiException.Conflict("不能将节点移动到自身子孙下");

        var newParent = await _db.Nodes.FirstOrDefaultAsync(n => n.Id == req.ParentId.Value, ct);
        if (newParent is null) throw ApiException.NotFound("ParentNode", req.ParentId.Value);
        if (newParent.MindMapId != node.MindMapId)
            throw ApiException.Conflict("父节点不属于同一导图");
    }
    // 后续两阶段平移逻辑不变
}

删除旧的两个私有方法：IsDescendantAsync（433-450）和 CollectDescendantsAsync（452-466）。

对比：三种做法

❌ 做法 A：只把递归换成「逐层查 + 参数化」

仍逐层 WHERE ParentId，只是加了缓存字典。治标不治本，深度大时仍多次往返。

✅ 做法 B（推荐）：共享索引 + 内存 BFS / 回溯

一次查询拉全部父子关系，删除走 BFS 向下、移动走回溯向上。两次往返都降到 1 次。

⚠️ 做法 C：MoveAsync 复用已查的兄弟节点

环检测只在「兄弟节点」里找，省一次查询，但逻辑脆弱——环可能跨多层，只看兄弟不够。

⭐ 做法 B 的额外收益

后续若加「移动子树前校验子树大小」「复制子树」「批量删除多节点」等功能，LoadParentRelationsAsync 可复用，不用再写一套递归。

副作用与边界

  • 内存开销：LoadParentRelationsAsync 只投影 (Id, ParentId) 两个字段（不拉 Title/Content 等大字段），N 个节点只占 N 个 Guid 对，几千节点也就几十 KB，可忽略。
  • 一致性：查询用 AsNoTracking，只读父子关系，不影响后续 SaveChanges 的变更追踪。
  • 并发：与现状一致——删除/移动本就不是高并发原子场景，且原代码也无锁，改造不引入新的一致性问题。
  • 索引：查询走 MindMapId 索引（NodeConfiguration.cs:48），一次扫描即得全量，比逐层 ParentId 查询更快（ParentId 本就无单独索引，逐层查其实是全表扫）。
  • 环检测正确性：原 IsDescendantAsync 用 visited 防死循环，新 IsDescendant 保留同样保护（即使数据异常成环也不死循环）。
唯一注意点：IsDescendant 的语义方向。原方法 IsDescendantAsync(candidateId, ancestorId) 是「candidate 是否在 ancestor 的祖先链上」，调用处传的是 (req.ParentId, id)——即「新父节点是否是被移动节点的后代」。改造务必保持参数顺序一致，否则环检测会判反，导致「移动到子孙下」漏检。建议给新方法加 XML 注释写明参数方向。
